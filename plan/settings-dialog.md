# 設定ダイアログと設定ファイルの統合

## 対象と現在の段階

- Issue #276
- 方針レビュー用。今回は調査と設計のみで、アプリの挙動や利用者の設定ファイルは変更しない。
- 目標は、たまに設定する利用者がキー名や構文を調べずに変更・保存できること。原則としてmacOS版の全公開設定を扱う。

## 方針

- 「Settings…」をアプリ全体の設定ダイアログにする。設定ファイルを永続化先とし、GUI専用の設定形式を別に増やさない。
- 型に応じた入力部品、説明、検索を提供する。設定キーそのものも検索できる。
- Save時に編集した設定だけを元のファイルへ反映する。実効設定全体を新しいファイルとして書き出さない。
- 既存のコメント、空行、順序、分割設定を保つ。手書き編集とGUI編集のどちらも継続できる。
- 既存の設定定義・パーサー・個別値の出力処理を共用する。UIはSwiftUI、設定の意味と検証はZig側が担当する。
- Markdown外部アプリの設定画面を統合し、独立したアプリメニューをなくす。

## 調査結果

### 再利用できる部分

- `src/config/Config.zig`が設定キーと型を定義している。宣言を調べた時点では公開設定は170項目。実装時には`Config.Key`から機械的に網羅性を確認する。
- `src/config/key.zig`は公開フィールドからキー一覧と値の型を生成している。
- `src/helpgen.zig`と`src/build/HelpStrings.zig`が設定コメント・キーバインドアクションの説明を生成し、`+explain-config`などで使っている。
- `src/config/formatter.zig`は真偽値・数値・enum・個別の複合型を設定形式に出力できる。
- `src/config/formatter_file.zig`と`+show-config`は設定全体や既定値との差分を出力できる。ただし、入力ファイルのコメントや構造を保存する用途には使えない。
- `Zashiki.Config`には読み込み、診断、複製、型ごとの値取得があり、`Zashiki.App.reloadConfig()`で保存後の反映を行える。
- `SettingsView.swift`は案内だけの未使用画面。「Settings…」は現在`AppDelegate.openConfig`から設定ファイルを外部エディターで開く。

### 保存で考慮する部分

- 現在の`LineIterator`はコメント・空白・引用符を除去する。保存用には元のバイト列と編集対象の範囲を別途保持する必要がある。
- 読み込みは既定値、標準ファイル群、CLI引数、`config-file`の参照先、finalizeの順。参照先はリストへ追加しながら処理するため、主ファイル末尾に書くだけでは必ずしも最後の設定にならない。
- macOSではXDGとApplication Supportの両方、旧形式と新形式が読み込まれる。保存先を固定して全設定を移すと既存の優先順位を変えてしまう。
- 相対パスは記述元ファイルを基準に展開される。検証用の別ディレクトリへファイルを移す方式では意味が変わる。
- テーマはfinalizeで読み込み、利用者の設定を再適用する。light/darkテーマの選択と内部の条件付き再生があり、現在の色を全部保存するとテーマへの追従を止めてしまう。
- 一般的な条件式を利用者が設定行に記述する構文は今回の調査では見つかっていない。内部の条件付き再生を、公開の条件式編集機能と混同しない。
- 既定値の全出力には明示すると競合する設定もあると既存テンプレートに記載されている。未変更の値や実行時に補完された値を書き込まない。
- `finalize`で数値を丸める項目があるため、診断がないことだけでは入力がそのまま採用された保証にならない。
- 外部アプリ設定は現在`MarkdownExternalApps`がUserDefaultsにJSON保存し、編集ごとに即時反映している。

## ダイアログ

- 左側にカテゴリ、上部に検索、右側に設定項目を表示する。カテゴリ案は「外観・フォント」「ウィンドウ・タブ」「入力・ショートカット」「マウス・選択・コピー」「シェル・動作」「通知」「Markdown」「詳細」。
- 「変更済みのみ」の表示を用意する。説明は行の近くに置き、詳しい説明は展開して読めるようにする。
- 各項目に現在の実効値と、このファイルで指定している値を区別して表示する。未指定はテーマ・他ファイル・既定値から継承する状態として扱う。
- 通常は現在の設定ファイルを自動選択する。設定が分割されている場合だけ、詳細表示で適用元と編集するファイルを確認・切り替えられるようにする。
- 右下にCancelとSaveを置き、編集は作業中の値に保持する。Saveまではファイルにも実行中アプリにも反映しない。閉じる際に未保存変更がある場合は保存・破棄・継続を選べる。
- 「このファイルでの指定を解除」は継承へ戻す操作。「アプリの既定値を明示設定」と区別する。テーマや他ファイルから継承する値があるため、両者を同じ操作にしない。
- 保存後は通常の再読み込みを行い、変更項目に応じて「新しいターミナルから反映」「再起動が必要」を表示する。再起動は勝手に行わない。
- ダイアログ内に「設定ファイルを開く」を残す。設定ファイルを直接開く既存のCLI・キーバインドアクションの意味は維持する。
- プレビューの「Configure External Apps…」は同じダイアログのMarkdownカテゴリを開く導線にする。

### 入力部品

| 型・用途 | 編集方法 |
| --- | --- |
| 真偽値・未指定を持つ真偽値 | スイッチと継承の選択 |
| enum | 説明付きの選択肢 |
| 数値・時間・サイズ・制限値 | 単位付き入力。自動・無制限などの状態を明示 |
| 色・テーマ・フォント | 色選択、テーマ一覧、フォント選択。light/darkを維持 |
| ファイル・ディレクトリ | 入力欄と選択ボタン。相対指定の基準を保持 |
| フラグの集合 | 個別のチェックボックス |
| 繰り返し文字列・環境変数 | 追加・削除・並べ替えできる一覧 |
| キーバインド | キー入力、修飾、アクションと引数、テーブル・連続キーの編集 |
| パレット・コードポイント・複合値 | 専用の表や複数入力欄 |
| 外部アプリ | 既存の名前・URLテンプレート・既定アプリの編集を移設 |

高度な設定にも説明と入力支援を用意する。「全設定」の完了条件を、構文そのままの文字入力欄を並べただけで満たしたことにはしない。

## 設定定義とGUIの接続

- Zig側で`Config.Key`を列挙し、キー、説明、型、選択肢、既定値、現在値を構造化してC API経由でSwiftへ渡す。通常のGUI操作でCLIプロセスを起動して出力を解析する方式にはしない。
- 既定値と実効値を別々に扱い、optionalの未指定と空文字・false・ゼロを区別する。
- 単純型とenumは自動的に入力部品を選ぶ。複合型には型ごとの編集・出力アダプターを登録する。
- カテゴリ、表示名、単位、適用タイミングなど、現在の型から分からないUI情報だけ追加定義する。数値制約は既存の意味と一致させ、パーサーにも共有できるようにする。
- 全キーが入力部品または意図した起動時専用の扱いへ対応していることを機械的に検査する。新しいキーがGUIから黙って欠落しないようにする。
- キーバインドでは既存のアクション定義と説明も使う。アクション引数の種類と編集部品を対応させる。
- C APIを拡張する範囲はスキーマ、編集用スナップショット、候補の検証・個別値のシリアライズとする。具体的なABIは実装開始時に固定する。

## 保存方式

### 元のファイルを保持して変更箇所だけ更新する

1. 読み込み時にファイルの元のバイト列、各行の範囲、キー・値の範囲、改行形式、ファイル識別情報を保持する。意味の判定は既存パーサーへ委譲する。
2. 編集は一度に一つのファイルを対象にする。通常の保存先の選択は既存の設定ファイル選択処理に揃え、アプリが明示的な設定パスで起動した場合はそのパスを使う。
3. 値を変更したキーだけを更新する。無変更のSaveは書き込みを行わない。未知・旧形式の行も、編集しない限り元のまま残す。
4. 単一値は対象ファイル内の有効な最後の指定を更新し、指定がなければ追加する。指定解除はそのファイルの対象キーの指定を取り除き、以前の重複指定が復活しないようにする。コメントは残す。
5. リスト・map・キーバインドは、要素の順序、追加・削除・リセットの意味を型のアダプターで処理する。単一値と同じ「最後の行を置換」で済ませない。パレットも変更した要素だけを扱い、テーマ由来の値を固定化しない。
6. 参照先ファイルやCLIで上書きされる場合は、保存先の値と実効値の違いを表示する。利用者の確認なしに参照先へ追記したり、ファイルの優先順位を変更したりしない。参照先を編集する場合は対象を明示的に切り替える。
7. 同梱テーマは編集しない。個別の上書きは利用者の設定ファイルへ保存する。light/darkテーマの選択自体を失わない。

### 検証と書き込み

- 読み込み処理に、特定の元パスの内容だけメモリー上の候補へ置き換える入口を設ける。元のパスを基準に、標準ファイル・参照先・CLI・テーマ・finalizeまで既存と同じ順序で検証する。
- 候補の検証は設定ファイルの新規作成などの副作用を起こさない。保存先や参照先を先に書き換えて検証する方式は使わない。
- 読み込み時の診断も画面で確認できるようにする。診断が残る候補は通常のSaveで保存しない。finalizeによる丸めや項目間の影響も示す。
- 保存直前に対象と読み込み依存ファイルの変更を再確認する。外部変更があれば上書きせず、再読み込みと編集内容の再適用へ案内する。
- 対象ファイルと同じディレクトリの一時ファイルへ書き、検証済みの内容をatomic replaceする。保存前の復元用コピー、既存の権限、シンボリックリンク先を考慮する。失敗時は既存ファイルを保持する。
- 複数ファイルを一つのSaveで同時変更しない。設定参照の構成自体を変更する場合も、新しい参照先は別の編集対象として扱う。
- 保存成功後に再読み込みし、未保存状態を解除する。反映に失敗した場合は保存済みと反映済みを区別して知らせる。

## 外部アプリ設定の移行

- 外部アプリ一覧と既定アプリをZigの設定定義に追加する。名前、安定したID、URLテンプレートを持つ繰り返し設定と、既定IDを持つ設定にする。
- 任意のURLの`=`, `&`, 引用符などを壊さない可逆な入出力を用意する。具体的なレコード構文はパーサー・formatterの往復テストで確定する。
- ファイルでの明示指定を優先する。未指定と明示的な空一覧を区別し、空一覧で既存の登録が復活しないようにする。
- ファイル未指定で旧UserDefaultsに登録がある場合は、移行候補として読み込む。最初のSaveで設定ファイルへ保存する。設定画面を開いただけでファイルを書き換えない。
- 保存成功を確認してから移行完了を記録する。失敗時やCancel時は旧データを残す。移行後にファイル側の指定を消しても旧登録が復活しないようにする。
- URLの生成・検証と起動処理は既存のものを再利用する。編集時の即時保存をやめ、他の設定と同じSave/Cancelへ揃える。
- スクロール位置やウィンドウ状態などの一時的なUI状態はUserDefaultsに残せる。今回の「全設定」は利用者が選ぶ永続的な設定を対象とし、OSの権限許可を独自ファイルへ移さない。

## 代替案と判断

- **実効設定を全再生成**: 既存formatterは使えるが、テーマの色・実行時の補完値の固定化、コメントや読み込み元の消失があるため採用しない。
- **GUI専用の追加ファイルを常に最後に読み込む**: 手書き部分は保てるが、新しい優先順位と二つの編集先が増える。現行の参照先読み込みでは単純な末尾includeも最優先にならないため採用しない。
- **全項目をSwiftへ手で複製**: 定義と選択肢がずれるため採用しない。UI情報と複合型の編集部品だけ追加する。
- **一部の一般設定だけGUI化して終了**: 全設定へ届く目標は維持する。ただし保存基盤、単純型、複合型を順に実装して検証する。

## 実装順序とレビュー単位

1. **設定基盤**: スキーマ、読み込み元の記録、元ファイルを保持するモデル、候補の検証・差分保存。UIなしで往復・競合・失敗時を検証する。
2. **設定ダイアログ**: Settingsの入口、検索・カテゴリ、単純型、Save/Cancel、継承、適用タイミング、直接編集の共存。
3. **複合型の網羅**: リスト、フラグ、テーマ、色、パレット、キーバインド、アクション引数など。全キーの対応表で残りを確認する。
4. **外部アプリ統合**: 設定定義、UserDefaults移行、専用メニューの整理、プレビューから該当カテゴリを開く導線。
5. **実機確認**: 保存・再読み込み・再起動・外部編集・入力支援を一通り確認し、完了条件を満たしてからIssueを閉じる。

実装を複数PRへ分ける場合もIssue #276を継続し、最後の必要なPRがマージされるまで`wip`を維持する。今回の設計draft PRは方針レビューのために開き、まだマージしない。

## 検証計画

- スキーマの全キー網羅、enum・optional・フラグ・アクション引数、既定値と実効値の区別。
- 無変更時のバイト一致、コメント・BOM・CRLF・引用符・重複キー・未知キー・旧キーの保持。
- リストの順序・空リスト・明示リセット、mapの削除、キーバインドの追加削除と既定との関係。
- 標準ファイルの併存、ネストした参照先、相対パス、任意の設定パス、CLI上書き、light/dark切り替え。
- 外部変更、保存権限エラー、途中失敗、シンボリックリンク、保存後に反映できない場合。
- 旧外部アプリ設定の初回移行・Cancel・保存失敗・空一覧・移行後の再読込。
- 関連するZig/Swiftテスト、`just lint`、`just test-fast`。画面の表示と操作はPRに`needs-verification`を付けて確認する。

## 今回の検証結果

- リポジトリ内の設定定義・読込順序・出力処理・Swiftの入口を調査した。
- 設計資料のみの変更。アプリのビルド・機能テスト・画面検証はこの段階では実施しない。
