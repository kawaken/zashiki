# `entry-point` worktree運用が不成立だった場合のリバート

## 目的

次回の新規セッションで`entry-point`を基準にしたworktree開始手順を検証し、
運用が実際の環境で成立しなかった場合に、今回追加したルールを安全に戻せる
ようにする。

## 対象

- 対象はPR #107で`AGENTS.md`に追加した`entry-point` bootstrap手順と、
  linked worktree／サンドボックス権限に関する記述。
- PR #108で`docs/history/`へ移動した調査記録は、失敗の根拠として残す。
- `entry-point`ブランチを最新の`main`へ追従させたこと自体は、運用失敗時も
  原則として戻さない。必要性を別途確認する。

## 検証で見ること

1. 新規セッションが意図した`entry-point`上の`AGENTS.md`を参照する。
2. `main`の更新、`entry-point`の同期、task worktree作成が意図した順序で進む。
3. 作業用worktreeで編集・`git add`・commitまで、追加の権限承認なしに完了する。
4. 作業用worktreeが既に割り当てられている場合に、入れ子worktreeを作らずに
   作業できる。

## リバート方針

- サンドボックスの権限不足だけで手順が失敗した場合は、ルールのリバートでは
  なく、Codexの環境・権限設定の問題として記録する。
- `entry-point`手順自体が誤っていて作業開始を妨げる場合は、失敗ログと再現手順を
  追記したうえで、PR #107の変更をリバートするPRを作成する。
- リバート対象は`AGENTS.md`の有効なルールに限定し、調査履歴・Issue・PR履歴は
  削除しない。
- リバートPRの作成・push・mergeは自動で行わず、内容を確認してから実行する。

## 完了条件

- 検証結果がIssueに記録されている。
- 成功した場合はリバートせず、失敗した場合は原因に応じてリバート要否を判断
  できている。
- リバートする場合は、`AGENTS.md`がリバート後の既存worktreeルールと矛盾しない
  ことを確認する。

## 実装時の知見（2026-08-31）

- 検証失敗時に判断できるよう、権限不足と手順不備を別の扱いにした計画をIssue
  #109として作成し、PR #110でmainへマージした。
- この計画自体はドキュメントのみで、実際のリバートはまだ実行していない。
- `git diff --check origin/main HEAD`を実行した。ビルドとテストは実施していない。
